# Диагностика входа Instagram — 9 октября 2026

## Результат

На сервере проверен вход с сохранённым устройством через установленную
`instagrapi 3.0.20`, профиль Android `449.0.0.52.84`, транспорт `curl` / HTTP/2.
Новая авторизованная сессия не создана. Ошибка воспроизведена на запросе
отправки данных входа, а не при регистрации пользователя сервиса.

| Шаг CAA | HTTP | Результат |
| --- | --- | --- |
| Подготовка CAA | 200 | JSON, status=ok |
| Аттестация устройства | 200 | JSON, status=ok |
| Подготовка OAuth | 200 | JSON, status=ok |
| Получение ключа шифрования через `qe/sync` | 405 | Пустое тело; библиотека смогла получить ключи из заголовков и отправить следующий запрос |
| `caa/send_login_request` | 429 | Пустое тело, сервер proxygen-bolt, Retry-After отсутствует |

Отдельно проверен предусмотренный той же версией библиотеки `login_legacy()`.
Профиль устройства и версия библиотеки сохранены. Запрос `launcher/sync`
получил HTTP 200, а `accounts/login` — HTTP 429 с JSON-категорией
`Please wait a few minutes`. Переключение на этот метод проблему не решило,
поэтому автоматический fallback после 429 не добавлен.

Пароль, cookies, токены, тела запросов, произвольные заголовки и содержимое
ответов в отчёт не включены. Для проверки пароль передавался через stdin,
а сохранённые настройки устройства расшифровывались только внутри worker.

## Что установлено и что остаётся неизвестным

- Сбой происходит при создании новой сессии Instagram. Авторизация в
  InstaSurveillance работает независимо от этого запроса.
- Нельзя утверждать, что пароль неверен, весь аккаунт заблокирован или все
  запросы с IP сервера запрещены: подготовительные запросы прошли успешно.
- Пустой ответ CAA не раскрывает точное правило, по которому Instagram
  отклонил запрос. Сообщение legacy также не отличает ограничения аккаунта,
  маршрута, устройства и текущей попытки входа.
- Сценарий совпадает с открытой ошибкой библиотеки
  [#2852](https://github.com/subzeroid/instagrapi/issues/2852): официальный
  Instagram входит, сохранённая сессия работает, новый CAA-вход получает 429.
  [Комментарий сопровождающего](https://github.com/subzeroid/instagrapi/pull/2853)
  и [изменение 3.0.20](https://github.com/subzeroid/instagrapi/pull/2855)
  не подтверждают исправление этого случая.
- Локальный tgplanner закрепляет версии 2.x. В его локальной БД сохранённой
  сессии для проверяемого Instagram username нет. Работа другого аккаунта
  или другой установки tgplanner не доказывает работу этого аккаунта здесь.

## Изменения в нашем адаптере

- После авторизации больше не запрашиваются лента и Reels: идентичность
  по-прежнему проверяется отдельным `account_info()`. Это устраняет случай,
  когда отказ ненужного запроса ошибочно делает успешный вход неудачным.
- При ошибке сохраняются безопасные сведения о каждом выполненном шаге:
  фиксированная метка endpoint, HTTP-статус, вид ответа, категория ошибки
  из закрытого списка, наличие Retry-After, версия библиотеки и число запросов.
- Текущая дата больше не выдаётся API за срок снятия ограничения. При
  отсутствии реального будущего срока возвращается `next_allowed_at=null`.
- Интерфейс различает отказ создания сессии и вход через официальный Instagram.
  Он не обещает конкретное время повтора без соответствующего срока.
- В тесте сравниваются фактические параметры CAA credential POST нашего
  адаптера и исходного Client: они совпадают. Адаптер не меняет этот payload.

Эти изменения исправляют диагностику и лишние запросы, но успешный новый
вход не подтверждён. Проверяемый путь восстановления — действующая сессия
этого же аккаунта с проверкой идентичности либо исправление CAA upstream.
Повторение одинаковых парольных запросов после 429 не является исправлением.
