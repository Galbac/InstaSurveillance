Дата: 7 октября 2026. Основание: `ТЗ.md`, текущие backend/frontend, Compose, миграции, OpenAPI и сохранённые отчёты. Это ревью соответствия, а не новый прогон тестов или браузерная приёмка.

## Вывод

**ТЗ V1 выполнено не полностью.** Помимо непроведённой браузерной/облачной/live Instagram приёмки, в коде остались конкретные недоработки. Прежняя формулировка «остались только внешние проверки» была слишком широкой.

Наличие endpoint или компонента не означает выполнения всех деталей сценария. Процент готовности не рассчитывается: пункты разного объёма, а часть проверок не проводилась.

## Подтверждённые недоработки

### G-01. Отключение Instagram при недоступном auth-vault

ТЗ: §15.5, §14.4, A-32. Файл: `backend/app/modules/data.py`, `disconnect`.

Сейчас `Redis.from_url(...).delete(...)` вызывается до `db.commit()`, внутри транзакции с lock, без явно заданных socket timeouts и без обработки недоступности vault. При ошибке выполнение не доходит до commit удаления сохранённой сессии и увеличения generation. Это не доказанная утечка, но конкретное препятствие надёжному отключению.

Нужно: гарантировать локальный отзыв независимо от vault, отделить ограниченную по времени очистку secrets от DB-транзакции, проверить outage/cancellation. TTL остаётся страховкой для временных credentials. Best-effort revoke на Instagram сейчас также отсутствует; транспорт разрешает только аналитические операции. Требуется безопасный отдельный путь либо явно согласованное изменение этого пункта.

### G-02. CSV не соответствует всем выбранным фильтрам

ТЗ: F-12, §13.5, §16.2. Файлы: `frontend/src/features/changes.tsx`, `backend/app/modules/contracts.py: ExportInput`, `backend/app/jobs/exporter.py`.

Changes передаёт в export только search и comparison_id; relation/type отсутствуют в ExportInput. Поэтому экспорт включает события, скрытые фильтрами экрана. Sort списка людей также не передаётся в export; renderer задаёт свой порядок. Нужно передать/валидировать фильтры и сортировку и проверить эквивалентность списка и файла.

### G-03. PWA update flow

ТЗ: §9. Файлы: `components/providers.tsx`, `components/install-pwa.tsx`, `public/sw.js`.

SW регистрируется, но нет обработки updatefound/waiting/controllerchange и UI предложения обновиться. Нет координации с активной загрузкой. Нужно реализовать обновление без автоматической потери выбранного файла и проверить на устройстве.

### G-04. Аналитика реализована частично

ТЗ: F-09, §7.7. Файл: `features/analytics.tsx`.

Доступны размеры списков и взаимность. Нетто-прирост показан только в таблице. Нет отдельного графика изменений между снимками и сравнения периодов при достаточных наблюдениях. Нужно реализовать эти представления без выдуманной интерполяции.

### G-05. Неполное сохранение фильтров в URL

ТЗ: F-07. Файлы: `features/changes.tsx`, `features/analytics.tsx`.

People использует URL. Changes читает initial before/after, но выбранные relation/type/search/mode/days и дальнейший выбор пары не сохраняет в URL. Analytics period/range/metric также остаются локальными state. Нужно обеспечить воспроизводимый переход, reload и back/forward.

### G-06. Админка и глобальные лимиты

ТЗ: §5.1, §7.11. Файлы: `modules/admin.py`, `features/admin.tsx`.

GET overview отдаёт три лимита, но frontend даже не включает limits в ожидаемый тип и не отображает их. Администратор не может менять глобальные лимиты через интерфейс/API; изменения доступны через серверный env. Нужно показать лимиты и определить безопасное управление с аудитом либо согласовать env-only вариант. Наличие ADR не является согласием заказчика на исключение требования.

### G-07. Очистка истории отдельным действием

ТЗ: F-13. Файлы: `modules/privacy.py`, `features/history.tsx`, `features/settings.tsx`.

Есть удаление одного снимка, профиля и аккаунта. Нет команды/интерфейса удаления всей истории с сохранением профиля и подключения. Последовательное удаление снимков вручную не заменяет отдельный сценарий с единым подтверждением и статусом.

### G-08. Мобильные фильтры и skeleton

ТЗ: §8.4–8.5. Файлы: `features/people.tsx`, `features/common.tsx`, `app/globals.css`.

Фильтры постоянно находятся в toolbar; требуемого нижнего sheet на mobile нет. Загрузка показывается Loader, а не skeleton. Размеры/контраст/focus/text zoom нельзя считать проверенными по CSS — browser QA отсутствует.

### G-09. Карточка последнего импорта

ТЗ: §7.3. Файлы: `components/dashboard.tsx`, `modules/contracts.py: SummaryDTO`.

Обзор показывает snapshot/source и последние события, но не краткую карточку последнего импорта с его состоянием/ссылкой на результат. Нужно добавить данные и соответствующий компонент.

### G-10. Статус доставки email и jitter

ТЗ: §14.4. Файлы: `jobs/tasks.py`, `modules/extended.py`.

Outbox содержит attempts/delivery_state/last_error, но пользовательский API их не раскрывает безопасным owner-scoped DTO. Retry использует детерминированный backoff; случайного jitter нет. Нужно добавить bounded jitter и безопасный технический статус, не сообщая о прочтении письма.

### G-11. Клиентский контракт и отмена запросов

ТЗ: §10–11, §13.5. Файлы: `lib/api.ts`, `lib/workflows.ts`, backend `modules/extended.py`.

OpenAPI и generated-api существуют, все явно перечисленные маршруты §13.2/13.6 найдены после нормализации имён path parameters; всего 73 операции. Но Profile/Snapshot/Summary/Job и ряд feature DTO дублируются вручную. Несколько backend endpoints не имеют строгого response_model. Query functions не передают предоставленный TanStack AbortSignal в fetch. Нужно завершить типизацию и фактическую отмену устаревших HTTP-запросов.

### G-12. Ограничения модели данных

ТЗ: §12.1–12.2. Файл: `backend/app/models.py`, миграции.

API проверяет принадлежность; тесты изоляции есть. Однако comparisons содержит независимые FK before_id/after_id/profile_id, без составного ограничения, которое само запрещает снимки разных профилей. В snapshot_members нет отдельного source_timestamp, хотя схема ТЗ предусматривает nullable значение. Нужно добавить целевые constraints/миграции и metadata либо согласовать изменение модели. Это несоответствие требованию защиты в БД, не утверждение о найденном HTTP обходе авторизации.

### G-13. Эксплуатационные метрики

ТЗ: §18.2. Файлы: `main.py`, `core/metrics.py`, `deploy/monitoring/alerts.yml`.

Есть HTTP latency/errors, queue age, worker heartbeat, job duration, cleanup и backup age. Отдельно не измеряются parsing stage duration и доступность DB/storage; готовность агрегируется readiness. Disk alert покрывает scratch volume, но не отдельно DB/S3/backup. Нужно дополнить метрики/экспортеры и проверить доставку alerts в целевом окружении.

### G-14. Не все async ответы имеют Location

ТЗ: §13.4. Основные create/import/export/privacy ответы используют Location, но 2FA verify, disconnect, cancel и admin retry не выдерживают общий контракт. Для каждой async команды нужно определить status resource и выдать его URL либо документировать синхронную семантику. Нейтральные auth 202 намеренно не обязаны раскрывать чувствительный ресурс.

## Доказательства и ограничения

Сохранены результаты: 55 passed/1 skipped, Ruff/Pyright/frontend build, чистый stack workflow, isolated restore, advisory scan production images без findings. В данном ревью тесты и сканы заново не запускались. Нагрузочный отчёт сделан на glibc dev ASGI TestClient, а production теперь Alpine/musl — переносить цифры на новый runtime/облако автоматически нельзя.

A-11 проверяет SIGKILL отдельного процесса, который захватил задание, и восстановление на изолированной PostgreSQL. Это не полный kill-drill рабочего Celery container во время тяжёлого импорта. Отказ брокера проверен через реальный TCP refusal изолированного endpoint, не через остановку облачного Redis. Эти границы должны оставаться в статусе приёмки.

Не проведены: browser UI/end-to-end, 320/360/390/768/1024/1440px, 200% zoom, keyboard/screen reader, Android/iOS installation/update/logout/offline, реальные Instagram login/2FA/session (отложены пользователем), целевой cloud HTTPS/SMTP/S3/alerts, off-host backup lifecycle/RPO/RTO, rollback/outage, согласованный 4 vCPU/8 GB и frontend LCP/INP/CLS. Реальная допустимость хранения и реквизиты документов определяются владельцем.
