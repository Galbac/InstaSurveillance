# Промпт: полноценная админка InstaSurveillance

Ты работаешь в существующем репозитории InstaSurveillance. Реализуй полноценную административную панель с красивым, удобным русскоязычным интерфейсом и подключением ко всем существующим административным API. Расширь backend там, где текущих данных недостаточно для полезного интерфейса. Доведи работу до проверенного результата, а не до макета или плана.

## 1. Сначала изучи проект

Прочитай AGENTS.md и актуальные исходники. Не считай этот документ заменой анализа кода: контракты могли измениться.

Основные файлы:
- backend/app/modules/admin.py — административные маршруты, роли и MFA.
- backend/app/modules/contracts.py — DTO.
- backend/app/models.py — модели данных.
- backend/app/core/dependencies.py, security.py, commands.py, limits.py, mfa.py — авторизация, CSRF, аудит, лимиты, MFA.
- backend/app/cli.py — bootstrap-admin и recover-admin-mfa.
- backend/app/jobs — задания, outbox, сборы, сравнения, экспорты и обслуживание.
- backend/app/integrations/instagram.py — ограничения Instagram и обработка ошибок.
- frontend/src/features/admin.tsx и frontend/src/app/admin/page.tsx — текущая админка.
- frontend/src/lib/api.ts, generated-api.ts, workflows.ts — API-клиент и типы.
- frontend/src/features/common.tsx, компоненты кабинета и стили — существующая дизайн-система.
- docs/api/openapi.json, compose.dev.yml, тесты и документация интеграций.

Сохрани архитектуру: FastAPI, SQLAlchemy, PostgreSQL, Celery/outbox, Next.js App Router, React, TanStack Query, существующие формы, компоненты и иконки. Не вводи новый стек. Не обновляй зависимости без необходимости; перед изменением проверяй официальные версии, Python-совместимость и lock-файлы.

## 2. Обязательное покрытие существующих ручек

Все пути ниже начинаются с /api/v1/admin. Таблица фиксирует существующее поведение, которое нельзя незаметно ослаблять.

| Метод и путь | UI и поведение |
| --- | --- |
| POST /auth/mfa/challenge | Ввод TOTP или резервного кода; показать expires_at |
| GET /overview | Обзор: число пользователей, задания по статусам, лимиты, версия |
| GET /users | Таблица пользователей; cursor, limit 1–100 |
| POST /users/{user_id}/suspend | Блокировка с причиной 5–500 символов, только admin |
| POST /users/{user_id}/restore | Возврат доступа с причиной, только admin |
| GET /jobs | Таблица заданий; существующий фильтр status, cursor, limit |
| GET /jobs/{job_id} | Детальная карточка задания |
| POST /jobs/{job_id}/retry | Безопасный повтор технического задания |
| GET /support/tickets | Таблица обращений; cursor, limit |
| PATCH /support/tickets/{ticket_id} | Ответ до 5000 символов и статус open/in_progress/resolved |
| GET /audit | Журнал действий, только admin |
| GET /limits | Текущие глобальные ограничения, доступ admin/support |
| PATCH /limits | Изменение трёх ограничений с причиной, только admin |

Общие права: admin/support получают доступ после MFA; privileged_until действует максимум 15 минут и не дольше основной сессии. Обычный пользователь не получает административных данных.

Поддержка может читать пользователей, задания, обращения, обзор и лимиты, отвечать на обращения и выполнять разрешённый backend повтор технических заданий. Аудит, блокировка/разблокировка и изменение лимитов — только admin.

Блокировка отзывает сессии пользователя, приостанавливает профили и изменяет generation. Запрещена блокировка себя; пользователь в удалении не должен обрабатываться как обычный активный пользователь. После восстановления профили остаются на паузе. Объясняй это в подтверждении.

Повтор допускается только для failed import/comparison/export, ошибок storage_unavailable/temporary_unavailable/timeout, attempts < 3 и активного владельца. Connect/sync нельзя запускать этой кнопкой. Backend остаётся источником истины, UI не гарантирует разрешение по устаревшим данным.

PATCH /limits принимает instagram_sync_interval_hours, instagram_request_budget, user_storage_quota_bytes и reason. Ограничения могут только ужесточать политику окружения: интервал увеличить, бюджет и квоту уменьшить. Не превращай эту форму в способ обхода ограничений Instagram.

## 3. Структура интерфейса

Сделай отдельный административный layout и маршруты:
- /admin — обзор.
- /admin/users — пользователи.
- /admin/users/[id] — карточка пользователя.
- /admin/profiles — Instagram-профили и подключения.
- /admin/profiles/[id] — диагностика профиля.
- /admin/jobs — задания.
- /admin/jobs/[id] — детали задания.
- /admin/support — обращения.
- /admin/support/[id] — обращение и ответ.
- /admin/audit — аудит.
- /admin/limits — ограничения.
- /admin/system — состояние системы и хранение.

Новые страницы должны использовать новые административные endpoint'ы, если их данные отсутствуют в текущих DTO. Не подставляй чужие ID в пользовательские маршруты и не обходи проверку владельца. Не считай перечисленные новые страницы уже обеспеченными backend.

На больших экранах: боковая навигация, верхняя панель с хлебными крошками, поиском в текущем разделе, ролью, сроком MFA и ссылкой «В кабинет». На телефоне — компактная навигация и карточки/управляемый скролл таблиц. Активный раздел виден, deep link и обновление страницы сохраняют контекст.

## 4. Визуальный стиль

Развивай существующий стиль InstaSurveillance: светлый фон, фиолетовый акцент, спокойные оттенки статусов, аккуратные панели, ясная типографика и умеренные скругления. Интерфейс должен выглядеть как единый продукт с кабинетом.

Приоритет — удобство работы с данными. Не заполняй экран декоративными карточками и дублирующими метриками. Выравнивай числовые столбцы, используй достаточный контраст, показывай длинные идентификаторы сокращённо с доступным копированием. Email/username не должны ломать сетку.

Статусы, ошибки, типы заданий и действия показывай по-русски. Технический код оставь в раскрываемых деталях. Даты форматируй через Intl; явно обозначай часовой пояс, API хранит UTC. Квоту показывай в понятных единицах, перевод в байты валидируй без потери точности. Для отсутствующих значений используй «—», а не ложный ноль.

Каждому экрану нужны loading, empty, error, forbidden и MFA-required состояния. Skeleton не должен сдвигать макет. Действия показывают прогресс и результат; повторное нажатие во время запроса запрещено. Ошибка содержит понятный текст и копируемый request_id. Abort запроса не показывай как сбой сервера.

Формы имеют связанные label, ошибки у поля, клавиатурное управление, focus-visible. Dialog/drawer удерживает фокус и возвращает его инициатору. Значение статуса передаётся текстом, а не только цветом. Графики не должны обрезать подписи на краях.

## 5. MFA и жизненный цикл доступа

Устрани текущую зависимость доступа от локального authorized=true. Добавь защищённый GET /admin/auth/status или согласованное расширение существующего контракта для роли, текущего серверного времени и privileged_until. Для роли без действующей MFA endpoint возвращает только минимальные сведения о необходимости подтверждения, без административных данных. Не требуй действующей privileged-сессии, чтобы узнать, что она истекла.

После обновления страницы существующая действующая MFA-сессия должна сохраняться. При mfa_required прекрати polling, закрой доступ к чувствительным данным и очисти административный query cache. После повторного MFA восстанови маршрут и безопасные фильтры. Не воспроизводи автоматически незавершённую мутацию: оператор должен явно повторить действие.

При logout, смене пользователя или утрате роли очищай все административные запросы, включая overview, limits, карточки и страницы. Не сохраняй MFA-коды и административные данные в localStorage/PWA cache. Не вводи браузерное создание/восстановление MFA и повышение роли; текущие защищённые серверные команды сохраняются.

## 6. Полезные расширения backend — реализовать в этой задаче

### Пользователи
Добавь серверный поиск email/ID, фильтры role/status/verified и даты создания с ограничениями длины и диапазонов. Карточка пользователя: основные сведения, количество профилей, задания по статусам, состояние использования хранения и связанные обращения. История административных действий доступна только admin. Не возвращай секреты, токены и полные cookie.

### Профили и качество Instagram-данных
Добавь административный список/карточку профилей с владельцем, username, status, paused, датами последнего/следующего сбора, cooldown, последним безопасно сериализованным заданием и наличием подключения как boolean.

Для последнего снимка показывай фактические и ожидаемые followers/following, completeness каждого списка, итоговую completeness и источник. Пример: «Получено 603 из 610 подписчиков; 294 из 294 подписок». Отдельно показывай, какие списки пригодны для сравнения. Не объявляй недостающие 7 аккаунтов удалёнными/заблокированными без доказательств.

Детали сборов: запросы/страницы, причина остановки, безопасные provider_http_status/error_code, предупреждения и версия библиотеки, если эти сведения сохранены. Отсутствующие данные показывай как неизвестные. Не запускай Instagram-запросы при открытии админки и не выводи сырые provider payload/cookie/signed CDN URL.

Это диагностический раздел. Не добавляй обход cooldown, автоматический повтор входа, массовые сборы или просмотр списка подписчиков всех пользователей. Если нужна административная пауза профиля, реализуй отдельную явно ограниченную admin-команду с причиной, аудитом и корректной отменой через существующий механизм generation; возобновление не должно немедленно запускать сбор или снимать cooldown.

### Задания
Расширь фильтры: kind, status, error_code, user_id/profile_id, даты. Карточка: владелец/профиль, stage, attempts, created/updated/heartbeat, безопасные details, связанный snapshot/comparison/export. Добавь вычисляемые allowed_actions и причину запрета retry, используя единую серверную политику для UI и мутации.

Не считай возраст heartbeat универсальным признаком зависания: учти статусы и существующие timeout/lease правила. Не создавай общий «повторить любое» или прямой запуск Celery из браузера.

### Поддержка
Серверные фильтры статуса, категории, даты, request_id; карточка обращения и связь с владельцем. Сохрани существующее уведомление пользователю при ответе. Текущая модель хранит один ответ: не изображай выдуманную переписку. Поток сообщений/назначение оператора требуют отдельной модели и миграции и относятся к следующему этапу.

### Аудит
Фильтры actor/action/target/request_id/дата, cursor pagination. Понятные названия действий и просмотр безопасных metadata. Аудит нельзя редактировать/удалять через UI. Любая новая административная мутация записывает актор, действие, цель, request_id, причину и безопасное изменение до/после; секреты исключены.

### Обзор и система
Дополнительно агрегируй активных/заблокированных пользователей, состояния профилей, свежие ошибки заданий, частичные снимки и открытые обращения. Каждый KPI имеет точное определение, период и ссылку на соответствующий фильтр. GET /overview сейчас содержит только users/jobs/limits/release: новые показатели реализуй на backend.

Добавь защищённый системный read-only endpoint: наблюдаемая готовность БД/Redis/хранилища, число и возраст необработанных outbox, очереди и worker heartbeat только при наличии надёжного источника. Не выдавай process alive за работоспособность всех workers. Покажи время последней проверки; неизвестное состояние отличается от healthy.

Хранение: агрегированный размер FileObject, квоты и ожидающие удаления DeletionRequest без receipt_token. Не считай сумму размеров файлов точным размером диска/S3. Не возвращай внутренние DSN, env, service credentials или полный metrics endpoint в браузер.

## 7. Что оставить следующим этапом

Составь отдельный список предложений, не добавляя их молча в реализацию:
- Назначение оператора и SLA обращений, история сообщений.
- Аудируемые выгрузки административных списков с русскими колонками и минимизацией персональных данных.
- Настройка уведомлений о всплесках 429, зависаниях очередей и частичных сборах.
- История изменения лимитов и понятное сравнение с env-политикой.
- Плановая политика хранения и отчёты очистки с учётом резервных копий.
- Расширенное управление ролями/MFA: отдельное согласование требований и усиленная защита, без универсального редактора role.

Не добавляй impersonation, редактирование секретов, кнопку обхода Instagram-ограничений или разрушительные массовые действия как побочный эффект дизайна.

## 8. Контракты, производительность и безопасность

Сервер проверяет роль и MFA на каждом endpoint; скрытая кнопка не заменяет авторизацию. Для новых разрешений зафиксируй матрицу admin/support и тесты. Новые диагностические персональные данные по умолчанию доступны admin; support получает только поля, обоснованно необходимые поддержке.

Используй явные DTO и белый список details. Проверяй состояние владельца перед мутацией. CSRF и idempotency обрабатывай существующим API-клиентом и серверными механизмами там, где они применяются; не обещай идемпотентность только из-за наличия заголовка.

Поиск/фильтры выполняются в БД, не на первых 50 загруженных строках. Cursor привяжи к фильтрам; при смене фильтров сбрасывай страницы. URL хранит воспроизводимые безопасные фильтры, а поиски по персональным email не должны попадать в произвольные внешние аналитические системы. Добавь нужные индексы миграциями, избегай N+1, тяжёлых неограниченных counts и загрузки всех записей. Не внедряй OFFSET для глубоких страниц вместо существующего cursor-подхода.

TanStack Query: передавай AbortSignal, дебаунс поиска, отдельные ключи с фильтрами, корректная инвалидизация после мутаций. Polling нужен только активным заданиям/обзору, с разумным интервалом и остановкой при скрытой вкладке/потере MFA. Отсутствие backend-метрики не заменяй случайной демодатой в рабочем режиме.

Соблюдай async-границы проекта: не добавляй блокирующую сеть в async handlers. Схемы БД изменяй Alembic-миграциями. Перегенерируй OpenAPI и frontend types из фактического backend.

## 9. Порядок реализации

1. Проанализируй код и составь матрицу существующих/новых endpoint, DTO и прав; кратко сообщи найденные ограничения.
2. Реализуй admin layout, навигацию, MFA lifecycle и покрытие существующих ручек.
3. Добавь необходимые фильтры, DTO, карточки, миграции и диагностические разделы.
4. Синхронизируй OpenAPI/types и реализуй реальные состояния UI.
5. Пройди проверки и исправь ошибки. Если браузер доступен, проверь desktop/mobile, роли, истечение MFA, длинные значения и empty/error состояния. Если недоступен, прямо сообщи об этом, не утверждай визуальную проверку.
6. Обнови документацию: маршруты, матрица ролей, CLI-настройка MFA, новые поля, миграции, ограничения диагностики.

## 10. Критерии готовности

- Все 13 существующих admin endpoint имеют рабочее представление/действие в UI.
- Доступ admin/support проверен на сервере; обычный пользователь не получает admin-данные.
- MFA переживает refresh в пределах серверного срока; после истечения чувствительные данные скрываются и cache очищается.
- Блокировка, восстановление, retry, ответ и лимиты сохраняют существующие ограничения и аудит.
- Новые экраны обеспечены реальными endpoint и DTO; ограничения доступа между владельцами не обходятся.
- Частичные followers не создают ложных выводов об отписках; полные following можно диагностировать и сравнивать отдельно.
- Числа, графики, таблицы и длинные поля не обрезаются на desktop/mobile; интерфейс доступен с клавиатуры.
- Нет токенов, cookie, MFA seed, подписанных CDN URL и паролей в UI/логах/экспортах.
- Backend: pytest с PostgreSQL, Ruff, Pyright; frontend: typecheck, lint, существующие тесты и необходимые новые проверки; build, если позволяет окружение. Миграции проверены, schema/types актуальны.
- Добавлены содержательные тесты ролей/MFA, фильтров/cursor, retry, лимитов, диагностической сериализации и административных мутаций. Не подменяй их тестами, лишь повторяющими JSX.
- Финальный отчёт содержит реализованные разделы, новые API/миграции, результаты реально выполненных проверок и оставшиеся ограничения.

Начинай с анализа репозитория и затем выполняй реализацию до завершения. Рутинные обратимые изменения и проверки не требуют повторного разрешения. Не публикуй и не выполняй реальные разрушительные действия над пользователями ради демонстрации; проверяй их на тестовых данных.
